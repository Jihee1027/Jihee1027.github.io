CPU design · Purdue ECE 437 · Pair project

RISC-V Processor

  • SystemVerilog
  • RISC-V
  • QuestaSim
  • Vivado

I built a 32-bit RISC-V CPU twice, as a single-cycle design and as a five-stage pipeline, and compared them on the same program. The lesson I kept: passing every unit test did not prove the whole system worked.

My partThe forwarding unit, the integration of the five stages, the halt fix and the branch-predictor logic. My partner wrote the hazard unit, the assembly test programs and the forwarding-unit testbench.

1 hangthat every unit test missed: the connected CPU ran past the end of the program. Found in the system waveform and fixed.
1.20× – 1.29×faster than single-cycle on the same mergesort program, across four memory latencies.
76.5 MHzpipeline clock from synthesis, against 47.6 MHz for single-cycle.
212 → 116cycles on a loop test with the branch predictor, at memory latency 0.
01

The bug the unit tests did not catch

The hardest problem was not in any single block. Every unit testbench passed, and the pipeline still misbehaved once the blocks were connected.

Work

Integrating five stages that each passed their own testbench.

Problem

In the system testbench the simulation never finished: fetch stayed on, the PC ran past the program, and data went unknown.

Action

Halt depends on fetch, the enables and the flushes together, so I reworked the halt, flush and enable logic.

Result

Instructions in flight now finish, the PC stops, and the datapath halts cleanly. I now verify the unit, the connected units, then whole programs.
