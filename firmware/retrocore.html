RetroCore: the wireless controller link

  • ESP32
  • ESP-NOW
  • Embedded C
  • SPI
  • DE10-Nano FPGA
  • KiCad

RetroCore is a two-player game console built around an FPGA board. Two wireless ESP32 controllers send their input to an ESP32 hub, and the hub passes it to the FPGA over SPI. This page follows that link: how it works, why it dropped out, how I tested it, and what is still open.

My partI am the hardware lead on a team of four. I defined the electrical architecture and the 11 W power budget, brought up the boards, traced the controller dropouts to three causes, designed the add-on PCB and built the FPGA side. The controller boards and their firmware are my teammates' work. The hub's receive code was written with AI assistance; I found it was missing, then flashed and tested it on the boards.

12 bytesper SPI frame from hub to FPGA every 20 ms (50 Hz), at 1 MHz in SPI mode 0. The FPGA keeps a frame only if exactly 12 bytes arrive.
200 mstimeout: a controller the hub has not heard from is marked disconnected and its buttons are released.
3 causesbehind the dropouts, separated and tested one at a time. Two are fixed and one is still open.
11 Wpower budget at 5 V (2.20 A) with a 1.1 A fuse on the add-on board, from datasheets and bench tests.
01

How the input gets from thumb to screen

Each controller reads its joystick every 10 ms and broadcasts a packet every 20 ms. The hub collects both players and sends one fixed-size frame to the FPGA on its own 20 ms loop.

A

Controller

An ESP32-S2 or C6 reads X and Y on its ADC and debounces the buttons. Every 20 ms it broadcasts a 13-byte packet: a magic word (“RCP1”), a sequence number, X, Y and the buttons.

B

Hub

The receive callback runs in the Wi-Fi task. It checks the magic word, maps the sender's MAC address to player 1 or 2, counts gaps in the sequence number as lost packets, and copies the data inside a critical section so the main loop never reads half an update.

C

FPGA

The SPI receiver samples the bus on the 50 MHz system clock through synchronizers, and commits a frame only when chip-select rises after exactly 12 bytes. A short or long frame is dropped, so a bad frame never reaches the game.

02

Why the controllers dropped out

The link worked for a while and then stopped, or the player drifted down on its own. One fix would not have explained both, so I followed the data path end to end and looked for each cause separately.

Work

The controller-to-FPGA link and the joystick behavior on screen, assigned to me in Week 10.

Problem

Input dropped out at random, and the player sometimes moved down without a press.

Action

Read the hub and FPGA receive paths, separated three causes, fixed two and tested them on the boards.

Result

Controller to hub to FPGA to screen works, and the joystick moves on the HDMI image. The ADC2 fix and range tests are still open.

03

Turning a raw stick into a direction

A joystick does not sit at the middle of its range, and moving it up also moves X. The hub firmware handles both before it sends a direction to the FPGA. The numbers come from our controllers and the hub code.

Center tracking

The center measured at boot (about 666) was not where the stick rested later (about 592), so the hub tracks the resting center instead of trusting one boot reading.

Hysteresis

A direction turns on and off at different points (Y on at 200 and off at 120, X on at 100 and off at 60), so a stick resting near a threshold does not flicker.

Cross-talk

Pushing up moved X by +400 to +670 on its own. A rule ignores X in that case, so pressing up does not also register as a turn.

05

Verification on the FPGA side

The hub's frames end up in my FPGA design, so I verify that side in simulation and in the build itself.

Sprite engine testbench

I rebuilt the sprite engine in SystemVerilog on one 100.78 MHz PLL clock and wrote a 419-line testbench for it.

A bug the simulator missed

The simulator passed, but Quartus built a 16,384×8 RAM out of about 131,000 flip-flops. I gated the address so it maps to block RAM, and added a block-RAM check to the build script so the same mistake is caught automatically.

CPU and SoC

The CPU simulation passes 321 checks across 40 programs against an instruction-set model, with exact cycle counts. The whole-SoC simulation runs with 0 errors.

FPGA

The FPGA design: CPU, graphics and audio

In one week I went from placeholder modules to a whole SoC that compiles and simulates: a RISC-V core, bus, RAM, graphics, audio, controller input registers and clocks. The CPU writes the graphics through one memory map, and the video side reads on the pixel clock. The display path is implemented: pixel counters and sync generation feed the board's HDMI transmitter at 25.195 MHz.

A

CPU

A five-stage pipeline, because the FPGA's block RAM returns data one clock after the address. The simulator runs 40 programs against an instruction-set model and passes all 321 checks with exact cycle counts. Cycles per instruction are about 1.13.

B

Graphics

An 8×8 tile background, a sprite engine with line buffers, and a 256-color palette. The sprite engine now holds 1,024 sprites and can zoom 16×16 and add glow colors.

C

One clock

The CPU, sprite engine and video now run from one PLL, so no synchronizers are needed between them. Registering the branch redirect shortened the critical path and cost one extra bubble on a mispredict. Net speed is about 1.9×.

A bug Quartus found, not the simulator

Connecting the background index straight to the palette address made Quartus build a 16,384×8 RAM out of about 131,000 flip-flops instead of block RAM. I gated the address and added a block-RAM check to the build script so it is caught automatically. An earlier RAM initialization file caused the same problem.

06

The add-on board and power

The hub lives on a two-layer add-on PCB that plugs onto the FPGA board. I drew the schematic, directed the layout and checked every version in KiCad. Placement and routing scripts were generated with Claude's help.

Found by measuring the file

Measuring the routed board showed one I2S line twice as long as the other two (150 mm against 80 mm). Reading the controller schematic showed the I2C header on the wrong ESP32 pins and a regulator that cannot hold 3.3 V as the battery drains.

Power budget

FPGA board 1.40 A, ESP32 hub 0.50 A and audio 0.30 A: 2.20 A at 5 V, or 11.00 W, with a 1.1 A fuse on the add-on board.

07

Still open

What I am working on next for the link.

Confirm the drift

Move the S2 joystick to an ADC1 pin and repeat the test with Wi-Fi on, to confirm or rule out the ADC2 cause.

Measure the link

Packet loss at 5 m, reconnect time and two players at once, using the sequence-number gap count the hub already keeps.

Tune the feel

Joystick sensitivity still feels wrong in play. Tune the thresholds with players, not just bench readings.
