RetroCore Gaming Console

  • DE10-Nano
  • RISC-V
  • SystemVerilog
  • ESP32
  • HDMI
  • KiCad PCB

A standalone two-player game console built around an FPGA board. It runs a RISC-V core, draws graphics over HDMI, and uses wireless controllers and a custom add-on PCB.

My partI am the hardware lead on a team of four. I built the FPGA design (RISC-V pipeline, tile and sprite graphics, audio, clocks), traced and fixed the controller-to-FPGA link, drew the add-on PCB, and made the enclosure CAD. Teammates built the controller boards and firmware and the CPU's control unit, ALU and register file.

03

The FPGA design: CPU, graphics and audio

In one week I went from placeholder modules to a whole SoC that compiles and simulates: a RISC-V core, bus, RAM, graphics, audio, controller input registers and clocks. The CPU writes the graphics through one memory map, and the video side reads on the pixel clock. The display path is implemented: pixel counters and sync generation feed the board's HDMI transmitter at 25.195 MHz.

A

CPU

A five-stage pipeline, because the FPGA's block RAM returns data one clock after the address. The simulator runs 40 programs against an instruction-set model and passes all 321 checks with exact cycle counts. Cycles per instruction are about 1.13.

B

Graphics

An 8×8 tile background, a sprite engine with line buffers, and a 256-color palette. The sprite engine now holds 1,024 sprites and can zoom 16×16 and add glow colors.

C

One clock

The CPU, sprite engine and video now run from one PLL, so no synchronizers are needed between them. Registering the branch redirect shortened the critical path and cost one extra bubble on a mispredict. Net speed is about 1.9×.

A bug Quartus found, not the simulator

Connecting the background index straight to the palette address made Quartus build a 16,384×8 RAM out of about 131,000 flip-flops instead of block RAM. I gated the address and added a block-RAM check to the build script so it is caught automatically. An earlier RAM initialization file caused the same problem.

04

Controller link: why the signal drops

The controllers worked for a while and then stopped. The controller boards and their firmware are my teammates' work. The link from the controllers into the FPGA, and the joystick behavior on screen, became my job in Week 10, so I read the firmware and the FPGA receiver to find out why.

1

No receiver code

The hub firmware only sent a test pattern. It never received an ESP-NOW packet, so a real controller could not reach the FPGA. The FPGA accepts a frame only if exactly 12 bytes arrive per chip-select, so an older one-byte stub was dropped every time. I had the receiver written into the hub firmware.

2

Joystick pin on ADC2

On the ESP32-S2 controller, the Y axis sits on an ADC2 pin, and ADC2 reads fail while Wi-Fi is on. A failed read looks like Y = 0, which the hub reads as down pressed. This is the likely cause of the random downward movement. I have not confirmed it on the board yet.

3

No retry or timeout

ESP-NOW broadcast has no acknowledgment, so a lost packet is gone. The hub now treats a controller silent for 200 ms as disconnected and releases its buttons.

Result: the path from controller through hub and FPGA to the screen works, and the joystick moves on the HDMI image. Still open: the signal sometimes drops, the joystick sensitivity feels wrong, and I have not measured packet loss at 5 m (requirement: at least 99 percent), reconnect time (2 s or less) or two players at once.

05

Add-on PCB and power

A two-layer board plugs onto the DE10-Nano's two GPIO headers. It carries the ESP32 hub, USB-C power, the audio amplifier and the controller ports. I drew the schematic, directed the layout, and checked every version myself in KiCad. The placement and routing scripts were generated with Claude's help.

A

Audio changed after measuring

On a breadboard the first audio chain gave pitches within 1 percent, but also mains hum, weak bass and only about 0.25 W. I switched the board to I2S with a MAX98357A class-D amplifier, which removes the filter and the volume pot.

B

Found by measuring the file

Measuring the routed file showed one I2S line twice as long as the other two (150 mm against 80 mm), so I will shorten it. Reading the controller schematic showed the I2C header on the wrong ESP32 pins and a regulator that cannot hold 3.3 V as the battery drains.

C

Many versions

The board went through many placements and routes in two days. I opened every version in KiCad, ran the checks, decided what to change, fixed the findings and rebuilt the ground pour to the course's 12 mil rule, which KiCad's own check does not cover.

06

Still open

These are the items I am working on next, listed as they stand after the Critical Design Review.

Timing

The Quartus compile uses 2,764 of 41,910 ALMs, but setup slack at 100.78 MHz is −0.306 ns. This is my main open hardware issue.

Controller link

Fix the signal drops, move the S2 joystick to an ADC1 pin, tune sensitivity, and measure packet loss, reconnect time and two players.

PCB

Rerun the final design-rule check, shorten the long I2S line, check the 5 V trace widths, and get a staff review before ordering.

What carries over to process integration

The Quartus RAM bug and the measured PCB trace lengths both showed me that the first check can pass while the real result is wrong. I now add an automatic check after each fix.
