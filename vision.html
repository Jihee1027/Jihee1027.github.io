00

Learning the inspection system

Initial work focused on how the existing vision system evaluated each view, communicated results to the line, and recorded defect data in SPC and Spotfire. The role covered system support and operational improvements.

Inspection baseline

Each view, including the foil area and CIS, was checked for false positives, where good material was flagged, and false negatives, where defects passed undetected.

Why it came first

Normal data, images, and system behavior provided the baseline for investigating deviations.

01

Raspberry Pi image logging at the unloader

Work: image traceability at the unloader. Built a Raspberry Pi image-capture and logging system so inspection images could be stored, retrieved, and reviewed.

Master and slave

Slave Pis captured images and a master Pi coordinated them over the local network, with secured remote access.

ROI image capture and logging

Capture was synchronized with the inspection system and focused on a region of interest, so the stored images were the ones that mattered for defect analysis.

Central review

Images were logged centrally on an industrial PC for review and traceability.

Why it mattered

Linking images with production metrics made it easier to investigate a defect trend using the underlying inspection evidence.

02

Daily vision data and system-health review

Daily review compared vision and production data with the previous day's results. Morning checks identified changes and set priorities; follow-up work covered investigation, adjustment, and verification.

Morning

  • Reviewed overnight defect rates by view in SPC and Spotfire, looking for shifts and recurring patterns.
  • Checked for missed or false triggers, gaps in image logging, and system outages.
  • Separated false positives from false negatives, and checked the flagged cases against the stored images.
  • Decided what needed a recipe change and what needed a bench check.

Afternoon

  • Retrieved images and equipment logs for abnormal inspection views and compared them with production metrics to investigate the cause.
  • Adjusted the recipe, the camera, the trigger timing or the hardware, depending on what the evidence pointed to.
  • Rechecked the relevant data under normal production conditions to verify each change.
  • Wrote down what changed, why, and what to keep watching.

Later in the internship an automated reporting tool (section 06) sent production updates through the day.

03

Tuning the inspection program with production data

Reviewed false positives and false negatives by inspection view using SPC and Spotfire. Adjusted the relevant recipe, then checked the response against production images and subsequent inspection data.

Views behave differently

Foil, CIS, and other views had different failure patterns. Each was analyzed separately alongside the overall defect trend.

Two errors, one trade-off

Inspection thresholds can trade false positives against false negatives. Both were checked against production images before a recipe change was retained.

Results

False positives decreased by approximately 10% after tuning. Production images were reviewed before retaining each recipe change.

04

Recovering a vision system when it goes down

When a vision system went down, the first goal was to restore inspection safely and quickly. Recovery, however, was not the same as understanding why the failure occurred.

The routine

Restarted the vision program, reset the camera and trigger board, and reloaded the recipe. Verified PC-to-PC communication, the PLC connection, and image capture before considering the system restored.

The inspection gap

A trigger-board reset could break the association between inspection results and cells already moving through the line. Although the system appeared to recover, those cells could remain uninspected.

Action and result

Raised the issue with the vendor. Affected cells were marked NG instead of passing without inspection.

Recovery checks needed to cover inspection continuity as well as system availability. Documenting the reset gap and escalating it to the vendor addressed the risk of uninspected cells passing through the line.

05

Signal-level and hardware debugging

Recurring failures required checks beyond software. Equipment logs, oscilloscope traces, and logic-analyzer captures were used to investigate trigger timing, camera behavior, communication, and cabling.

Software symptom

Investigated missed or repeated inspections, image-logging gaps, and failures that returned after resets across software, communication, and hardware layers.

Signal evidence

Compared electrical waveforms and trigger timing with digital communication captures, equipment logs, and production data.

Interface or hardware cause

Investigated CIS hardware and cable connections, then identified and corrected a cable-related issue affecting system behavior.

06

Production and POR reporting automation

Built a Python tool to deliver production and POR updates every hour, replacing manual data collection. The design accounted for the team's reporting needs and operation on an unattended Windows PC.

What it tracked

The Windows application used Python and Win32 APIs to track production and POR data from the plant's production systems.

Every hour

Automatic hourly reports gave the team current production figures throughout the shift.

Results

Inspection throughput increased by about 7.2% after the tool was introduced. Absolute production volumes remain confidential.

The sections below show how the reporting workflow behaves. Room names, targets and addresses are left out, and the code itself stays private.

Work

Hourly production and POR reporting on Windows, using timestamped summary emails and a saved snapshot to track changes.

Problem

The team needed timely production and POR reports without manual data collection or duplicate messages.

Action

Built a Python application for Windows to detect new reports, parse and compare data, and send messages through a single queue with section-level checkpoints.

Result

The workflow tracks sent sections to avoid duplicates and resumes unfinished reports after a restart. Reports that fail parsing are logged and withheld. Usage counts remain confidential.

Prevent duplicate reports

Each email is identified by its timestamp. Multi-part reports are checkpointed section by section, so a crash halfway through resumes at the missing part.

Withhold reports that fail parsing

If an email cannot be parsed, the application logs the failure and moves to the next task without sending an incomplete or unreliable report.

Highlight changes since the last report

Each report is compared with the last saved snapshot so the team can see what changed.

07

Extending the reporting workflow to images

Extended the text-reporting workflow toward line-photo delivery. Upload, batching, and archive logic reached prototype stage; end-to-end delivery remained in development at the end of the internship.

  • Implemented Text reporting: the report cycle above.
  • Prototype Photo upload, batching and archive logic.
  • In progress Delivering image batches end to end.

Upload and send are separate by design

The planned workflow had devices upload files whenever they were ready and trigger a send once. The server would reply immediately and a background worker would handle the rest, so a slow send would not block the device.

Handling late uploads

In the design, a folder would be queued once. If a trigger arrived while it was being processed, it would be marked pending and run again afterward. Sent files would be archived into dated success or fail folders with a history log.
