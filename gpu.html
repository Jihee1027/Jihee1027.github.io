GPU Vertex Stage

  • SystemVerilog
  • FPGA
  • Fixed point
  • Pipelining

The vertex stage of a GPU datapath, in fixed point. It transforms vertices, divides by w, and converts normalized coordinates into screen space. The work is in progress.

Problem

A vertex stage has to transform vertices, divide by w and convert to screen space, one vertex after another, in fixed point and inside an FPGA's resource and clock budget.

Data

Design targets of 100 MHz, 10M vertices per second and 60 FPS; a 24-bit Q16.8 format; RTL test results and a timing run.

Action

Split the work into transform, perspective-divide and screen-space modules, then built the perspective-divide prototype and tested it.

Result

The prototype passes 14 directed tests and accepts one vertex per cycle in simulation. An earlier Artix-7 implementation run at a 125 MHz stretch target did not close timing. The other modules are still in progress.

Process integration context

The vertex-stage project made timing margin, pipeline depth, numerical precision and implementation constraints concrete. It gives me another view of the downstream side of process integration: device and interconnect behavior eventually becomes implementation margin at the circuit and system level.

01

What it is

Three pipelined RTL modules with fixed-point interfaces: a 4×4 model-view-projection transform, perspective division, and a screen-space transform that outputs screen X and Y plus depth. Values are 24-bit signed Q16.8. There is no lighting stage.

02

Where it stands

The perspective-divide module is the implemented prototype. It computes a reciprocal of w and multiplies x, y and z by it, with divide-by-zero and saturation handling, passes 14 directed tests, and accepts one vertex per cycle in simulation. The input FIFO, the screen-space transform and integration are in progress. The design target is 100 MHz, 10M vertices per second and 60 FPS; a 125 MHz stretch run did not close timing (worst negative slack −1.751 ns).

03

What I have to balance

Numerical precision, FPGA resource usage, clock frequency and pipeline throughput. Improving one usually costs another.
