GPU Vertex Stage

  • SystemVerilog
  • FPGA
  • Fixed point
  • Vivado
  • Python

I am building the first stage of a small FPGA GPU for Purdue SoCET. It takes each 3D triangle and converts it into 2D screen coordinates, in fixed-point math, so the next stage can draw it.

My partI cut the stage from 40 to 13 DSP slices (measured each block, then changed each one), added the clipping stage that drops triangles behind the camera, ran the top-level verification, and built the FPGA test harness. Noah Zhu wrote the first version of the row-serial multiplier; I finalized it and re-integrated it. Team of three.

40 → 13DSP slices used, out of 120 on the chip (10.8%). The target was 15 to 20.
+0.388 nssetup slack at the 125 MHz clock after routing in Vivado. Positive slack means the timing is met.
761 / 761top-level checks pass across 15 testbenches, compared with a bit-accurate Python model.
27 cyclesper triangle, inside the 30-cycle budget. That is 13.9 million vertices per second against a 10 million requirement.

02

Cutting DSP slices from 40 to 13

DSP slices are scarce on this FPGA, and the rest of the GPU needs them too. I measured where the 40 went, then changed each user one at a time and re-ran the tests after every merge. The price is a longer pipeline, which still fits the 30-cycle budget.

A

Reuse one multiplier

The matrix multiply now reuses three multipliers over the four matrix rows, taking one vertex every 4 cycles. Noah Zhu wrote the first version; I finalized it and integrated it again without changing the interfaces. It uses 6 slices.

B

A table for 1/w

A 256-entry table with linear interpolation replaces the iterative reciprocal. It needs 1 slice, and the latency drops from 11 to 5 cycles. The table fits in logic, so no block RAM is used.

C

Shifts for ×640 and ×480

The screen scaling uses shifts and additions instead of multipliers, so that step needs 0 slices. The perspective multiply keeps 6 slices, one multiplier per coordinate.

03

Clipping, level 1

Before this sprint, a vertex behind the camera produced a wrong triangle. I added the cheapest fix: drop it. A vertex with w ≤ 0 or z + w < 0 leaves with w = 0, the perspective divide reports a divide by zero, and the output FIFO drops the triangle. No other module had to change.

What it covers

Triangles behind the camera or in front of the near plane are dropped whole. A triangle that crosses the near plane is dropped, not cut into smaller ones. It costs one cycle, a few comparators and one adder.

What it does not cover yet

The far plane and the side planes pass through unchanged, so the rasterizer would have to clamp them. I chose the level that is easy to extend, because the rasterizer interface is still undefined.

04

The whale test, and what blocks it

To show the stage working on hardware, I built a harness that sends a 145-triangle whale through the real stage on the AMD Urbana board and returns every output over UART. A script compares each output with the bit-accurate model and draws the picture.

Blocker 1: the board is not detected

The lab PCs do not see the board's USB chip at all, on Linux or Windows, and a second board behaves the same. Since this is not about the bitstream, I built an LED-only test to tell board problems from design problems. Next step: try another lab or PC.

Blocker 2: the harness misses 125 MHz

The harness ends 0.184 ns short at 125 MHz, although the vertex stage alone meets it. I built it at 100 MHz instead, which is enough to check correctness and latency. I have not yet read the worst path.

In the close-up view, 30 of the 145 triangles lie in front of the near plane and are dropped by the clipping stage, so 115 remain. That is the number the board run should reproduce.

What carries over to process integration

Two habits from this project are the same ones I used on the manufacturing line: measure before changing anything, and keep what is verified apart from what is not yet tested.
